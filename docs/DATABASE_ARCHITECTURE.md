# Database Architecture

## Decision

PostgreSQL is the system of record for BISP EPM Automation. Oracle Planning
continues to own Planning metadata and financial data; PostgreSQL stores only
platform identity, configuration, orchestration, audit, scheduling, and agent
state.

SQLAlchemy owns database access and transaction boundaries. Alembic is the
only component allowed to create or alter production tables. Application
startup may verify the schema revision, but repositories must never mutate the
schema.

## Design principles

- Use UTC `TIMESTAMPTZ` values for persisted instants.
- Use `BOOLEAN`, not integer flags.
- Use `JSONB` for immutable/versioned documents and variable maps whose keys
  are defined by Oracle, not by this platform.
- Use relational tables and foreign keys for identities, ownership, execution
  state, schedules, and other data queried or joined by the platform.
- Use `VARCHAR` plus application enums/check constraints instead of native
  PostgreSQL enums so status values can evolve safely.
- Preserve display values while enforcing case-insensitive uniqueness with
  functional indexes on `lower(...)`.
- Prefer soft archival only where users expect history: schedules and reusable
  run profiles. Platform users are deactivated rather than deleted.
- Do not persist Oracle passwords, API keys, uploaded file contents, Planning
  data grids, or generated reports in the database.

## Tables

### Identity and access

#### `platform_users`

| Column | Type | Rules |
|---|---|---|
| `user_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Primary key |
| `username` | `VARCHAR(80)` | Required; unique on `lower(username)` |
| `display_name` | `VARCHAR(120)` | Required |
| `email` | `VARCHAR(254)` | Optional; unique on `lower(email)` when present |
| `password_hash` | `TEXT` | Required; password hashes only |
| `is_active` | `BOOLEAN` | Required, default `true` |
| `failed_login_count` | `INTEGER` | Required, default `0`, non-negative |
| `locked_until` | `TIMESTAMPTZ` | Optional |
| `created_at` | `TIMESTAMPTZ` | Required |
| `updated_at` | `TIMESTAMPTZ` | Required |
| `last_login_at` | `TIMESTAMPTZ` | Optional |

#### `platform_roles`

Stable enterprise roles. `role_id` is an identity primary key; `code` is a
unique immutable business key. Role definitions are seeded explicitly by a
deployment/bootstrap service, not by table creation.

#### `platform_role_permissions`

Many-to-many role-to-permission assignment with primary key
`(role_id, permission_code)`. Deleting a role cascades its grants.

#### `platform_user_roles`

Many-to-many user-to-role assignment with primary key `(user_id, role_id)`.
It also records `assigned_at` and optional `assigned_by_user_id` for audit.

#### `authentication_events`

Append-only authentication audit containing event type, username snapshot,
optional actor user, success flag, IP address, timestamp, and JSONB details.
The username is copied deliberately so the event remains meaningful if the
account is later renamed.

#### `api_tokens`

Revocable credentials for trusted external clients such as the Excel Pipeline
Runner. Each token belongs to one active platform user and carries an explicit
scope list. Only a SHA-256 digest and a short non-secret prefix are stored; the
secret is returned once when issued. Expiry, revocation, and last-use fields
support operational control and audit without storing Oracle credentials in a
workbook.

### Oracle and process configuration

#### `oracle_pipelines`

Administrator-approved Oracle Pipeline catalog with natural key `code`, name,
description, and audit timestamps. Pipeline runtime variables and stages stay
in Oracle and are discovered live; they are not duplicated here.

#### `planning_processes`

Stable root record for a platform process. `process_code` is the primary key.
Versions, run profiles, and schedules reference this table rather than a
mutable active version.

#### `planning_process_versions`

Immutable process versions with composite primary key
`(process_code, version)`. Stores status, process definition JSONB, cycle
definition JSONB, creation time, and activation time. A partial unique index
allows at most one `ACTIVE` version per process.

The two documents remain JSONB because they are read and activated as one
versioned aggregate. Splitting every Pipeline step and Oracle variable binding
into separate tables would add joins without improving integrity.

#### `process_run_profiles`

Reusable, non-secret runtime context. Stores common Year/Period/Scenario/
Version fields plus JSONB maps for Oracle variables, Inbox references, and
required local-upload keys. An archived profile is retained for execution
history; active profile names are unique within a process.

#### `process_schedules`

One recurrence definition per row, referencing a process and optionally a run
profile. Stores IANA timezone, local first-run time, next UTC run, enabled and
archive state, and the last scheduler outcome. `last_execution_id` is a
correlation value rather than a foreign key because a scheduler handoff can
receive an external execution identifier before local workflow persistence.
A partial due-work index supports scheduler polling without scanning archived
or disabled schedules.

### Operational Planning work

#### `planning_cycles`

One dated business cycle such as `August Forecast FY27`. This is deliberately
different from `PlanningCycleDefinition`, which remains reusable technical
configuration for an Oracle Pipeline-backed process. The operational cycle
stores business context, dates, status, creator, and an optional reference to
the reusable platform process.

#### `planning_cycle_stages`

Ordered business lifecycle stages such as reconciliation, planner input,
review, and reporting. These rows provide business progress and never copy the
technical stages already owned by Oracle Pipeline.

#### `planning_tasks`

Actionable work assigned to exactly one platform user or platform role. A task
stores business context and a governed action handoff, but it never stores
credentials or directly grants permission to execute the action.

#### `planning_task_dependencies`

A minimal directed dependency graph. Readiness is computed from prerequisite
task status rather than duplicated in a mutable column. The application
rejects self-dependencies, unknown tasks, and dependency cycles before insert.

### Execution and audit

#### `execution_queue`

Durable work accepted by the web/API layer before any Oracle action starts.
Each row contains a versioned, credential-free JSONB command, target identity,
priority, status, worker lease, heartbeat, attempt count, and terminal error.
PostgreSQL workers claim rows with `FOR UPDATE SKIP LOCKED`. A partial unique
index prevents concurrent queued/running work for the same target.

An expired `RUNNING` lease becomes `RECOVERY_REQUIRED`; it is never
automatically requeued. This avoids silently executing a non-idempotent Oracle
job twice when the first worker's final outcome is uncertain.

#### `workflow_runs`

One durable automation execution. Stores a 64-character execution/correlation
ID (normally a UUID), workflow name, status, UTC timestamps, error message,
triggering source, and immutable username/display-name snapshots. The
snapshots are intentional because
scheduled/API actors may not map to a retained platform user.

#### `workflow_steps`

Ordered steps for a workflow run. Composite primary key
`(execution_id, sequence)`, with status, timestamps, JSONB details, and error.
Deleting a workflow run cascades its steps.

### Agent state and audit

#### `agent_conversations`

User-owned conversation metadata: UUID, owner, title, provider/model snapshot,
and timestamps. Message content is kept outside operational workflow tables so
agent retention can be managed independently.

#### `agent_messages`

Ordered user/assistant messages for one conversation. Deleting a conversation
cascades its messages.

#### `agent_tool_activities`

Append-only audit of allow-listed tool calls. Stores the tool name, redacted
arguments JSONB, status, summary, and timestamp. Raw credentials and Planning
data grids are prohibited.

#### `agent_action_drafts`

Non-executable action handoffs associated with a conversation and assistant
message. Structured requirements, stages, input schema/value maps, and
preflight checks are JSONB because they are provider-neutral versioned
documents. Draft records never represent approval or execution.

## Required indexes

- Unique `lower(platform_users.username)`.
- Unique `lower(platform_users.email)` where email is not null.
- Descending `authentication_events.occurred_at`.
- Unique API-token prefix and hash; index on `(user_id, revoked_at)`.
- `workflow_runs.started_at DESC` and `(status, started_at DESC)`.
- Partial unique active process version per process.
- Partial unique active profile name per process.
- Partial unique active schedule name.
- Partial schedule due index on `(next_run_at)` where enabled and unarchived.
- Partial unique active Planning-cycle code.
- Planning cycles on `(status, due_date)`.
- Unique stage code and sequence within a Planning cycle.
- Planning tasks on assignee, status, and due time.
- Agent conversations on `(user_id, updated_at DESC)`.
- Agent messages on `(conversation_id, message_id)`.
- Agent tool activities on `(conversation_id, created_at)`.
- Agent drafts on `(conversation_id, created_at)`.
- Durable queue claims on `(status, available_at, priority, created_at)`.
- Active durable targets uniquely on `(job_type, lower(target_key))` while
  status is `QUEUED` or `RUNNING`.

## Migration policy

1. Every schema change is represented by a reviewed Alembic revision.
2. Deployments run `alembic upgrade head` once before web or scheduler workers
   start.
3. Application startup checks that the database is at the expected revision
   and fails clearly when it is not; it never creates tables automatically.
4. Autogenerated migrations are a starting point and must be reviewed for
   constraints, indexes, data conversions, locking, and reversibility.
5. Backward-compatible changes use expand/migrate/contract:
   - expand: add nullable columns/tables/indexes;
   - migrate: deploy code and backfill in bounded batches;
   - contract: make fields required or remove obsolete structures later.
6. Destructive production changes require a backup and normally use a forward
   repair migration instead of relying on downgrade.
7. CI creates an empty database, upgrades from base to head, runs integration
   tests, and verifies that Alembic reports a single current head.

## Initial cutover

The Alembic revision chain creates the schema above in an empty PostgreSQL
database. Revision `0001_platform_schema` establishes the platform,
`0002_cycle_task_engine` adds operational cycles and tasks, and
`0003_external_api_tokens` adds revocable external-client credentials.
Revisions through `0008_artifact_registry` add governance and environment-
scoped Oracle catalogs; `0009_durable_execution_queue` adds production worker
dispatch and leases; and `0010_unified_oracle_catalog` extends the same
environment catalog to Business Rules, Data Maps, import jobs, Cube Refresh
jobs, and Planning cubes without creating a duplicate registry table.
